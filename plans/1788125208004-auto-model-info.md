# Auto-derive reasoning support and generate a model_info.yaml draft

## Decisions

**Upstream advertises SUPPORT, never the effort enum.** Verified live: OpenRouter
`/models` and `/models/{id}/endpoints` both carry `reasoning`, `reasoning_effort`,
`include_reasoning` inside `supported_parameters` and no list of levels anywhere;
deepseek/kimi `/models` return only `id/object/owned_by`. So `allowed:` stays an
operator decision in `models.yaml`; only `reasoning.supported` is derivable.

**Derive it in the normalizer, not the service.** `_normalize_openrouter`
(`src/core/model_capabilities.py:209`) already copies `supported_parameters`
verbatim; the same function sets `reasoning: {"supported": True}` when that list
contains `reasoning` or `reasoning_effort`. This REVERSES the decision recorded in
the `normalize_provider_model` docstring (`src/core/model_capabilities.py:261`,
"upstream 'reasoning' ... is NOT translated into our reasoning{} block") — that
paragraph is rewritten in the same commit to say what is now true: `supported` is
auto-derived, `default_enabled` / `effort_levels` stay manual-or-derived-from-policy.

**Precedence needs no change.** `_resolve_stored_capabilities`
(`src/services/model_service.py:89`) already layers
`merge_capabilities(merge_capabilities(cache, derived), model_info)` and merges
dicts key-wise, so a cached `reasoning.supported` sits under the `effort_levels`
derived from `models.yaml` and under `model_info.yaml`. The invariant holds as
written.

**The generator is a printer over the cache, never a writer.** `scripts/dump_model_info.py`
follows the shape of `scripts/probe_models.py`: standalone CLI, never imported by
the app, prints a YAML draft to stdout for human review. It reads the already
normalized `data/model_cache.json` (`CapabilitiesCache` stored form == the
`model_info.yaml` stored schema, stated at `config/model_info.yaml:10`), so there
is no second normalizer to keep in sync and no network call.

## Risks

* Reversing a recorded decision: mitigated by rewriting the docstring paragraph in
  the same diff, so the marker never contradicts behaviour.
* `/v1/models` is an exact-surface assertion in tests — a new `reasoning` key on
  cached OpenRouter models can break a totality assertion. Grep the payload
  assertions before implementing.
* The cache file lives in the container volume; the script must take a path
  argument so it also runs against a copy on the host.

## Order

1. One commit: normalizer derivation + docstring rewrite + `scripts/dump_model_info.py`
   + unit tests.

## Not doing

* Scraping llama-server `/props` (`chat_template_caps.supports_reasoning_effort`,
  `modalities`) — a second upstream call per refresh, separate task.
* Inventing `effort_levels: [low, medium, high]` from a bare `reasoning_effort`
  support flag. Nothing upstream says those are the values.
* Writing `config/model_info.yaml` from the script. Output is reviewed by hand.
* Deriving `reasoning.default_enabled` — not expressible in any upstream shape.

## Validation

* `pytest tests/unit/test_model_capabilities.py tests/unit/test_model_service.py -q`
  plus the `tests/api/` files touching `/v1/models`.
* New tests: OpenRouter entry with `reasoning_effort` in `supported_parameters`
  yields `reasoning.supported`; an entry without it yields NO `reasoning` key;
  a `models.yaml` policy still supplies `effort_levels` on top of the cached
  `supported`; `model_info.yaml` still overrides both.
* Live: `docker compose up -d --build`, then
  `curl -s localhost:8777/v1/models -H "Authorization: Bearer <key from config/user_keys.yaml>"`
  and show `gemini/mini` carrying `reasoning.supported: true` sourced from the
  cache alone (it has no `reasoning_effort` block in `models.yaml`), and
  `local/reasoner` still carrying its `effort_levels`.
* Script: `docker compose exec api python scripts/dump_model_info.py --path /app/data/model_cache.json`
  — capture the printed YAML verbatim and confirm it re-parses as the stored schema.
