# Release v1.1.0 — 2026-10-01

10 commits (merges excluded) since v1.0.1. The headline theme is a router chained behind
another router: the external router now advertises the same reasoning options the main
router enforces, and `/v1/models` never advertises a default reasoning effort that the
router itself would reject.

version: v1.1.0 — a patch was recommended (fix×2, no feat); the operator chose a minor:
the reasoning block of `/v1/models` carries more fields for chained-router clients.

# What changed for clients

## Reasoning options through a chained router

- A client of a router chained behind another router (the ext router in front of main) now
  sees the upstream's `reasoning.effort_levels`, `default_effort` and `default_enabled`
  in `/v1/models` and `/v1/capabilities`, instead of a bare `supported: true`. Observed on
  ext: `glm/flash` → `[low, high, max]`, `deepseek/flash` → `[low, high]` with
  `default_enabled: true`.
- A model the main router serves from a generic upstream (e.g. `glm/flash` via z.ai) is
  listed by main with nothing but its reasoning block; the ext router used to cache such a
  model empty and show no reasoning options at all. It now keeps them.
- An ext-side `reasoning_effort` policy in `models.yaml` still replaces the upstream's
  effort levels, so what `/v1/models` shows stays equal to what the router's own gate
  enforces.

## Default effort never outside the advertised levels

- Real OpenRouter entries carry their own effort vocabulary (e.g. `default_effort:
  minimal` or `medium`). When that default falls outside the model's `effort_levels`, it
  is no longer shown in `/v1/models` — a client that sent it back would get a 400 from the
  router's effort gate.
- The operator gets a one-time WARNING per model naming the value, the levels and the
  config fix. Note: the text log format does not print `error_type`, so search with
  `docker logs <container> 2>&1 | grep "upstream default_effort"`, not by
  `capabilities_config_conflict`.

# Internal (no client-visible change)

- The project is renamed to `llm-api-gateway` (GitHub `kreolsky/llm-api-gateway`); the
  `usage_data` volume keeps its pinned name.
- Release notes are English-only, enforced by the Cyrillic gate; a stray CI workflow of
  another project is removed; plans untouched for 90 days are archived.
- The effort-policy `default:` is documented as used where two model ids split one
  upstream model by effort; a lesson on round-trip test fixtures is added.

# Upgrade actions

- `main`: `3d28f14` → this release's SHA (fast-forward).
- Upgrade via `deploy-server`, code-only: `requirements.txt` and `Dockerfile` are
  unchanged, so rsync `src/` + `docker compose restart` is enough. Both prod routers
  (`server-ai-api` and `server-ai-api-ext`) already run the code of this release
  (`v1.0.1-8-g14ed0af`); redeploying only restamps `/health`.
- No new env vars. The usage DB schema does not change.
- Prod configs (edited by hand on the server, already applied):
  - main `models.yaml`: `gemini/mini` `allowed: [minimal]`; `gemini/flash`
    `allowed: [low, medium]`, `default: medium`; `gemini/pro` `allowed: [medium, high]`,
    `default: high`. A client sending `minimal` to `gemini/flash` or `low` to
    `gemini/pro` now gets a 400 `invalid_parameter_value`.
  - ext `user_keys.yaml`: `/v1/capabilities` added to `allowed_endpoints` of every key.
- After deploy: `ssh docker "curl -s localhost:8777/health"` →
  `{"status":"ok","version":"v1.1.0"}`.

# Known limitations

- The ext router's cache of main's capabilities refreshes every
  `MODEL_CACHE_REFRESH_INTERVAL` (default 3600s); a policy change on main reaches ext
  clients after the next refresh or an ext restart.
- `default_enabled` from OpenRouter is now advertised for OpenRouter-backed models; a
  harness that reads it may enable reasoning where it previously did not.
