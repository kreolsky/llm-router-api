# Release v1.0.0 — 2026-09-27

The first versioned release: 192 commits since the project began (2025-07-06), 40 of them (merges excluded) after the previous state of `main` (`1ca9a40`). The router is an OpenAI-compatible gateway to multiple LLM providers (DeepSeek, z.ai, Kimi, OpenRouter, local models) with per-key access control, transparent streaming and usage accounting. Starting with this release the version is visible in `/health`, and the project is distributed under the MIT license.

version: v1.0.0 — chosen by the operator; the commits recommended a minor (feat×22), but there was no previous tag and the client contract is considered settled.

# What the router does

## For clients

- One endpoint for every provider: `/v1/chat/completions` (streaming and not), `/v1/embeddings`, `/v1/audio/transcriptions`, `/v1/models`, `/v1/models/{id}`, `/v1/capabilities`.
- Streams are forwarded byte for byte; the OpenAI `reasoning` field is duplicated into the llama.cpp `reasoning_content` field. An upstream error before the first byte arrives with its real HTTP status (401, 429), not as a 200 with an error inside.
- `/v1/models` returns a model's full capability set: context, output limit, modalities, supported parameters, pricing. The manual `model_info.yaml` catalog always wins over the upstream auto-cache.
- Every error uses the OpenRouter format `{"error": {"code", "message", "metadata"}}`, including requests to nonexistent paths.

## Reasoning

- Each model can restrict the accepted `reasoning_effort` values (`models.yaml` → `reasoning_effort.allowed`): a value outside the list is a 400 naming the field, never a silent substitution.
- Each provider declares a dialect (`providers.yaml` → `reasoning_dialect: openai | deepseek | openrouter`): the same `thinking` / `reasoning_effort` pair from the harness is translated into the shape a given upstream understands.
- `/v1/capabilities` returns a flat `{supported, effort_levels}` map over the models available to the key.

## Reliability

- A config reload no longer cuts off streams in flight: old connection pools are closed only after their requests finish. Unchanged providers survive the reload together with their pool.
- A reload that applied only partially shows up in the logs as a failure and is retried, instead of looking successful.
- An optional per-provider concurrency limit (`max_concurrent`): excess requests wait for a slot and get a 503 on timeout.
- Upstream 429s are retried with exponential backoff.

## Usage and statistics

- One row per request (errors included) in SQLite; the cost is frozen at write time from the model's pricing.
- The `/stat/` dashboard, broken down by key and model; wide tables scroll inside their cards.

## Client-visible changes in this sync

- The `/tools/generate_key` endpoint is removed; keys are generated by `scripts/generate_key.py`.
- `/health` returns `{"status": "ok", "version": "…"}` — a new field; the existing one is unchanged.

# Upgrade actions

- `main`: `1ca9a40` → `40f897e` (fast-forward).
- Prod checked against the release: `requirements.txt` and `Dockerfile` match; in `src/` only `api/main.py` differs (the version field). Upgrade via `deploy-server`, code-only: rsync `src/` + write `src/VERSION` + `docker compose restart`, no rebuild.
- No new env vars.
- Prod configs are untouched: `reasoning_dialect` in the server's `providers.yaml` is already set, and `reasoning_effort` in `models.yaml` is optional.
- The usage DB schema does not change.
- After deploy: `ssh docker "curl -s localhost:8777/health"` → `{"status":"ok","version":"v1.0.0"}`.

# Known limitations

- A single uvicorn worker only (`API_WORKERS=1`): the model capabilities cache and the usage writer live in-process.
- The list of headers not forwarded upstream under `identity: passthrough` is a denylist ("only what is listed is blocked"): an unknown client header goes upstream. The list must be re-audited whenever a new harness or proxy is onboarded.
