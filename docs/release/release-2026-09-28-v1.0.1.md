# Release v1.0.1 — 2026-09-28

17 commits (merges excluded) since v1.0.0. The headline theme is honest error handling and accounting: upstream errors in a stream are visible to the client and in the statistics, llama-server streams are finally recorded with token usage, and a broken config is rejected immediately and unambiguously. Under the hood — a large architecture cleanup with no change to client responses.

version: v1.0.1 — a minor was recommended (feat×2); the operator ruled both feats internal: neither the response shape nor the endpoints changed.

# What changed for clients

## Errors in a stream

- When the upstream refuses a streaming request (429, 5xx), the client receives the upstream's own error text instead of the placeholder "Unable to read error response from provider".
- An exhausted connection pool to a provider is now always a 503 `service_unavailable` ("retry later"), streaming or not; previously the non-streaming path answered 500 `provider_network_error`.
- When llama-server fails after the 200 and sends an `{"error": {...}}` frame, the frame still reaches the client as is, but the request is no longer recorded as a success: the statistics show it with `error_code=provider_stream_error` and the upstream's error text (the HTTP status stays 200 — that is what the client received).

## Usage accounting

- Streams to llama-server are now recorded with tokens: the router adds `stream_options: {include_usage: true}` itself when the client did not send it. A `stream_options` set explicitly by the client (including `include_usage: false`) is forwarded unchanged; non-streaming requests are not touched.
- Prices in `model_info.yaml` written like `1e-7` (which YAML reads as a string) no longer break the cost calculation or lose the usage row: the price is coerced to a number, and a non-numeric / `nan` / `inf` / negative one is dropped with a warning — the row is written without a cost instead of disappearing.

## Configuration

- A config error (unknown `reasoning_dialect`, `identity` or provider type, an invalid static header) vetoes the reload and the old config keeps running; at startup it refuses to start. A rejected config is logged once, not every 5 seconds until the file is fixed.
- `max_concurrent` must be a positive integer: the string `"3"` used to silently disable the limit and `true` became a limit of 1 — both are now config errors.
- Dangling cross-file references (a model pointing at a nonexistent provider, a key with an unknown model in `allowed_models`) produce a warning in the log.
- A malformed env var value (a number that does not parse; a bool other than `true`/`false`) refuses startup, listing every bad variable. Empty/unset values still take the defaults.
- A request arriving during a config reload can no longer get a body shaped for a different backend than the one it was actually sent to: the reasoning dialect is taken from the provider being called.

## Logs

- Tracebacks in `warning`/`info`/`debug` with `exc_info=True` are no longer lost.
- An upstream error in a stream is logged as one line, without a second ERROR with a traceback.

## Internal (no client-visible change)

- One `Provider` class instead of a base class with a single subclass; the provider registry is an object injected via `app.state`.
- YAML is parsed once into a typed `RouterConfig`.
- One model resolver (access → existence → provider) for dispatch and `/v1/models/{id}`.
- The usage writer receives its pricing function by injection; all 13 `/stat/api/*` responses are pinned byte for byte by a golden test.

# Upgrade actions

- `main`: `40f897e` → this release's SHA (fast-forward).
- Upgrade via `deploy-server`, code-only: `requirements.txt` and `Dockerfile` are unchanged, so rsync `src/` + `docker compose restart` is enough.
- No new env vars. The values of existing ones are now validated strictly at startup — checked on prod: every set value is valid.
- Prod configs are untouched. The new strictness can refuse startup on an error in `providers.yaml`: on prod `max_concurrent: 3` (an integer) and `reasoning_dialect` is one of the accepted values.
- The usage DB schema does not change.
- After deploy: `ssh docker "curl -s localhost:8777/health"` → `{"status":"ok","version":"v1.0.1"}`.

# Known limitations

- Models that spend a small `max_tokens` entirely on reasoning (DeepSeek V4 Flash) can return an empty `content` — this is upstream behaviour; the router does not alter the response.
