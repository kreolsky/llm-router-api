# Что изменилось для клиентов

## Ошибки в стриме

- Если апстрим отказал стриминговому запросу (429, 5xx), клиент получает текст ошибки самого апстрима, а не заглушку «Unable to read error response from provider».
- Исчерпанный пул соединений к провайдеру теперь всегда 503 `service_unavailable` («повторите позже») — и в стриме, и без него; раньше не-стрим отвечал 500 `provider_network_error`.
- Если llama-server упал уже после 200 и прислал кадр `{"error": {...}}`, кадр по-прежнему уходит клиенту как есть, но запрос больше не записывается как успешный: в статистике он виден с `error_code=provider_stream_error` и текстом ошибки апстрима (HTTP-статус остаётся 200 — это то, что получил клиент).

## Учёт расхода

- Стримы к llama-server теперь записываются с токенами: роутер сам добавляет `stream_options: {include_usage: true}`, если клиент его не прислал. Явно заданный клиентом `stream_options` (включая `include_usage: false`) пересылается без изменений; не-стрим запросы не трогаются.
- Цены в `model_info.yaml` вида `1e-7` (YAML читает их как строку) больше не ломают расчёт стоимости и не теряют строку статистики: цена приводится к числу, нечисловая / `nan` / `inf` / отрицательная отбрасывается с предупреждением — строка пишется без стоимости, а не пропадает.

## Конфигурация

- Ошибка в конфиге (неизвестный `reasoning_dialect`, `identity`, тип провайдера, недопустимый статический заголовок) отвергает перезагрузку, старый конфиг продолжает работать; при старте — отказ запуска. Отвергнутый конфиг логируется один раз, а не каждые 5 секунд до правки файла.
- `max_concurrent` должен быть положительным целым: строка `"3"` раньше молча отключала лимит, `true` превращался в лимит 1 — теперь это ошибка конфига.
- Висячие ссылки между файлами (модель на несуществующего провайдера, ключ с неизвестной моделью в `allowed_models`) дают предупреждение в логе.
- Некорректное значение env-переменной (число, которое не парсится; bool не `true`/`false`) — отказ запуска с перечнем всех плохих переменных. Пустые/незаданные значения по-прежнему берут умолчания.
- Запрос, пришедший во время перезагрузки конфига, больше не может получить тело, сформированное под другой бэкенд, чем тот, куда он реально ушёл: диалект reasoning берётся у вызываемого провайдера.

## Логи

- Трейсбеки в `warning`/`info`/`debug` с `exc_info=True` больше не теряются.
- Ошибка апстрима в стриме логируется одной строкой, без повторного ERROR с трейсбеком.

## Внутреннее (без видимых клиенту изменений)

- Один класс `Provider` вместо базового класса с единственным наследником; реестр провайдеров — объект, внедряемый через `app.state`.
- YAML парсится один раз в типизированный `RouterConfig`.
- Один резолвер модели (доступ → существование → провайдер) для dispatch и `/v1/models/{id}`.
- Запись usage получает функцию цен через внедрение; все 13 ответов `/stat/api/*` закреплены golden-тестом байт в байт.

# Действия при обновлении

- `main`: `40f897e` → SHA этого релиза (fast-forward).
- Обновление — `deploy-server`, code-only: `requirements.txt` и `Dockerfile` не менялись, достаточно rsync `src/` + `docker compose restart`.
- Новых env-переменных нет. Но значения существующих теперь проверяются строго при старте — на проде сверено: все заданные значения корректны.
- Конфиги прода не трогаются. Новая строгость может отказать в старте при ошибке в `providers.yaml`: на проде `max_concurrent: 3` (целое), `reasoning_dialect` — из допустимых значений.
- Схема usage DB не меняется.
- После деплоя: `ssh docker "curl -s localhost:8777/health"` → `{"status":"ok","version":"v1.0.1"}`.

# Известные ограничения

- Модели, тратящие маленький `max_tokens` целиком на reasoning (DeepSeek V4 Flash), могут вернуть пустой `content` — это поведение апстрима, роутер ответ не меняет.
