# Plan: per-provider SOCKS5 proxy support

## Context
Некоторые бэкенды нужно достигать только через SOCKS5-прокси (напр. для гео-обхода/изоляции сети). Задача: разрешить пускать весь трафик конкретного провайдера через SOCKS5-прокси, задаваемый в конфиге провайдера (`providers.yaml`). Прокси без авторизации; инфраструктурный тестовый прокси — `proxy.red:1331`. Прокси задаётся per-provider, поэтому провайдеры без ключа `proxy` ходят напрямую как сейчас.

Так как каждый провайдер владеет своим `httpx.AsyncClient`, прокси естественно ложится на конструктор клиента (`proxy=` у httpx).

## Changes

### 1. `src/providers/base.py` — прокинуть proxy в клиент
- В `__init__` (рядом с чтением `base_url`/`headers`, ~стр. 94-96) прочитать:
  ```python
  self.proxy = config.get("proxy")
  ```
- В `_build_client` ([base.py:140](src/providers/base.py#L140)) передать прокси в оба ветвления (`config_manager` есть / нет):
  ```python
  return httpx.AsyncClient(limits=limits, timeout=timeout, proxy=self.proxy)
  ```
  `proxy=None` — это дефолт httpx (прямое соединение), так что провайдеры без ключа не меняют поведения.
- Обновить docstring `__init__`/`_build_client` и добавить `# ARCH:` заметку: прокси per-provider, задаётся ключом `proxy` в `providers.yaml`, `None` = напрямую.

Формат значения (решено): **полный URL со схемой**, напр. `socks5://proxy.red:1331`. Никакой нормализации в коде — значение передаётся в httpx как есть. httpx требует схему; неверный URL всплывёт на fail-fast старте.

### 2. `requirements.txt` — SOCKS-зависимость
httpx умеет SOCKS только с пакетом `socksio`. Изменить строку `httpx>=0.27.0` на:
```
httpx[socks]>=0.27.0
```
Это тянет `socksio`. Без него httpx кинет `ImportError`/`ProxyError` при построении клиента с `socks5://`.

> Замечание: в локальном venv стоит httpx 0.25.2 (где параметр называется `proxies=`, а не `proxy=`). Docker-образ ставит из requirements (`>=0.27`), где `proxy=` корректен. Продакшн/тесты идут через Docker, так что ориентируемся на 0.27+. Локальный прямой запуск pytest без апгрейда httpx может падать — стоит подтвердить, что тесты гоняются в Docker (skill `run-tests` так и делает).

### 3. `config/providers.yaml` — включить прокси на `openrouter`
Добавить в блок `openrouter` (стр. 10-16) строку:
```yaml
    proxy: socks5://proxy.red:1331
```
Именно этот провайдер должен ходить через SOCKS5. Остальные провайдеры остаются без `proxy` (прямое соединение).

### 4. Документация
- `CLAUDE.md`: в разделах "Provider Abstraction" / "Configuration (YAML)" упомянуть опциональный ключ `proxy` (SOCKS5) per-provider.
- Опционально `RULES.md`, если там перечислены ключи провайдера.

### 5. Unit-тесты
В `tests/unit/test_base_provider.py::TestClientOwnership` (после стр. 451):
- `test_provider_with_proxy_builds_client`: инстанцировать `ProviderStub` с `config["proxy"] = "socks5://proxy.red:1331"` — `provider.client` строится без ошибок, `provider.proxy` установлен.
- `test_provider_without_proxy_defaults_none`: провайдер без ключа `proxy` — `provider.proxy is None`.

## Reuse / trace
- Клиент строится только в одном месте: [base.py:_build_client](src/providers/base.py#L140). Прокси применится и к обычным, и к SSE-запросам, т.к. оба используют `self.client`.
- Кэш провайдеров пересобирается атомарно при reload ([providers/__init__.py:rebuild_provider_cache](src/providers/__init__.py#L67)) — смена `proxy` в конфиге подхватится после reload, как и `max_concurrent`. Отдельных изменений в фабрике не требуется (config dict передаётся целиком).
- Стартовая fail-fast валидация уже инстанцирует всех провайдеров → неверный proxy URL всплывёт на старте.

## Verification
1. **Rebuild образа** обязателен — `httpx[socks]` тянет `socksio`.
2. Unit-тесты: `python -m pytest tests/unit/test_base_provider.py -v` (в Docker).
3. E2E через Docker (skill `run-tests`): модель `gemini/mini` через `openrouter` — успешный ответ через SOCKS5. Проверить и стрим.
4. Регресс: провайдеры без `proxy` работают как раньше напрямую.
